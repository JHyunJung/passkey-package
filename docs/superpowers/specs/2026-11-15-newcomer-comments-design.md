# 신규 개발자용 주석 정비 — 설계

2026-11-15

## 1. 의도

Java 는 능숙하지만 Kotlin 과 이 프로젝트는 처음인 개발자가 코드를 읽고, 고치고, 운영할 수 있게 한다.
수단은 주석뿐이다. 동작은 한 글자도 바뀌지 않는다.

지금 코드는 주석이 적지 않다(본 코드의 15~25%). 문제는 양이 아니라 다음 세 가지다.

- 작업 흔적 표기(`Phase 3 T5`, `P1:`, `Phase QW-3`, `codex P2:`, "원 Java 는 …")가 본 코드 주석에 수백 곳 있다.
  당시 작업자에게만 뜻이 있고, 처음 보는 사람에게는 잡음이다.
- Java 개발자가 잘못 읽기 쉬운 Kotlin 지점(`!!` 199곳, `?:` 145곳, `companion object` 60곳, `@field:`·`@get:` 류 51곳)에
  이유가 없거나, 있어도 "원 Java 와 같은 자리"처럼 지금은 존재하지 않는 코드를 가리킨다.
- 주석이 하나도 없는 파일 55개 중 일부는 이름만으로 역할을 알기 어렵다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
- 처음 보는 사람이 각 모듈의 진입점과 요청 흐름을 주석만 따라가도 잡을 수 있다.
- Kotlin 을 모르는 Java 개발자가 "이 줄을 Java 식으로 고치면 깨진다"는 지점을 그 자리에서 안다.
- 이번에 추가하거나 고친 주석 문장은 전부 지금 코드에 대해 참이다.
  손대지 않은 기존 주석의 전수 대조는 하지 않는다. 다만 읽다가 코드와 어긋난 기존 주석을 발견하면 그 자리에서 고친다(발견한 것만).

**비목표**
- 테스트 코드, HTML 템플릿, SQL, yml, 스크립트, 빌드 파일(`*.gradle.kts`)의 주석.
- 영어 주석의 한국어 번역. 정확한 영어 주석은 그대로 둔다.
- 식별자 이름 변경, 포맷 정리, import 정리, 코드 이동. 주석 아닌 줄은 건드리지 않는다.
- 별도 안내 문서 작성. (기존 `docs/superpowers/notes/kotlin-conversion-patterns.md` 는 손대지 않는다.)

**실패 조건 (기술적으로 끝나도 실패로 본다)**
- 주석을 뺀 소스가 작업 전과 한 줄이라도 다르다.
- 코드와 맞지 않는 주석이 하나라도 들어갔다. 틀린 주석은 없는 것보다 나쁘다.
- 보안·동시성·계약 근거를 담은 기존 주석이 사라졌다.
- 주석이 기계적으로 보인다(3절 금지 목록).
- 모든 클래스·메서드에 고르게 주석이 붙었다. "필수적인 것만"이 요청이다.

## 3. 주석 규칙

### 3.1 어디에 쓰는가

쓴다:
1. **진입점과 흐름** — 애플리케이션 클래스, 필터(순서 포함), 컨트롤러가 받는 경로, 서비스의 처리 단계, 스케줄 잡.
   "요청이 어디로 들어와 어디로 나가는가"를 따라갈 수 있을 만큼만.
2. **이유가 코드에 안 보이는 곳** — 보안 판단, 동시성·락, 트랜잭션 경계, 순서 의존, 외부 계약(RP API·DB 스키마·세션 직렬화),
   일부러 느리게/이상하게 해 둔 곳, 고치면 안 되는 값.
3. **Java 개발자가 잘못 읽는 Kotlin** — 3.3 절.
4. **이름만으로 역할을 알 수 없는 타입** — 한두 줄.

쓰지 않는다:
- 이름과 시그니처가 이미 말하는 것(getter, 단순 DTO, 위임만 하는 메서드).
- 코드를 한국어로 다시 읽어 주는 문장.
- `@param`/`@return` 을 이름만 반복하는 KDoc·Javadoc.

**주석이 하나도 추가되지 않는 파일이 많은 것이 정상이다.** 파일마다 뭔가 넣으려 하지 않는다.

### 3.2 작업 흔적 정리

대상 표기: `Phase N…`, `Task N`, `T5`, `P0-2`·`P1:`·`S9`·`F02`·`G07` 같은 감사·백로그 번호, `QW-3`, `spec §`, `followup`,
`codex …`, "원 Java"·"기준 Java"·"Java 원본"·"Kotlin 전환"·"전환 전", 그리고 같은 성격의 다른 표기.
(기계적 패턴은 후보 목록일 뿐이다. `P256`, `F5` 키, `S256` 처럼 도메인 용어는 대상이 아니다.)

처리:
- **번호·단계 표기만 붙은 경우** — 표기만 지우고 설명은 남긴다. `/** P1: BCrypt 검증 성공을 기억하는 시간. */` → `/** BCrypt 검증 성공을 기억하는 시간. */`
- **"원 Java 와 같은 자리" 류** — 지금 코드가 왜 그렇게 동작해야 하는지로 다시 쓴다.
  `// !!: 원 Java v.getId().toString() 의 NPE 와 같은 자리.` 는 "id 가 null 이면 여기서 NPE 가 나야 하고, 바깥 catch 가 무엇으로 처리한다"처럼
  현재 동작과 그 동작에 기대는 쪽을 적는다. 기대는 쪽을 코드에서 확인하지 못하면 고쳐 쓰지 말고 표기만 걷어낸다.
- **Java 언어와의 비교는 남긴다.** "Kotlin `trim()` 은 유니코드 공백까지 자르므로 Java `String.trim` 과 같은 판정을 쓴다"는 독자에게 유용하다.
  지워야 하는 것은 "예전 Java 구현"을 가리키는 말이지 Java 언어 자체가 아니다.
- **흔적 표기뿐이고 내용이 없는 주석** — 삭제한다.
- 영어 주석 안의 표기는 영어 문장을 유지한 채 표기만 걷어낸다. 번역하지 않는다.
- 아직 열려 있는 백로그 항목을 가리키던 번호는 지우되, 미해결 제약이라는 사실이 주석에 필요하면 내용으로 풀어 쓴다.
- **없어진 Flyway 버전 번호**(`(V18)`, `V36 의 …` 등 약 27곳) — 마이그레이션은 squash 되어 V1~V6 만 남았다. V7 이상을 가리키는
  번호는 지우고 설명(어떤 컬럼·제약·프로시저인지)은 남긴다. 새 객체명을 SQL 에서 찾아 바꿔 쓰는 작업은 하지 않는다.
  지금도 존재하는 V1~V6 참조는 그대로 둔다.

3.4 절의 문체 금지 목록은 새로 쓰거나 고치는 주석에만 적용한다. 기존 주석을 문체 때문에 고치지 않는다.

### 3.3 Kotlin 주석

문법 강의는 하지 않는다. **Java 식으로 읽거나 고치면 동작이 달라지는 자리**에만 쓴다. 대표적으로:

- `!!` — null 이 올 수 없는 이유, 또는 일부러 NPE 를 내는 이유와 그 예외를 받는 쪽. 자명한 `!!` 에는 쓰지 않는다.
- `@field:` / `@get:` / `@param:` — 애너테이션이 어디에 붙는지를 명시하는 표기다. "타깃을 빼면 검증이 조용히 빠진다"고 쓰지 않는다:
  이 프로젝트의 Kotlin 2.4.21 은 타깃 없는 애너테이션을 생성자 파라미터와 필드 양쪽에 붙인다(컴파일 후 javap 로 확인, 2026-11-15).
  타깃이 동작을 실제로 가르는 경우(`@field:Value` 주입, `@get:` 직렬화 등)만 그 자리에서 확인하고 쓴다.
- 요청 DTO 의 nullable 필드 + 제약 — non-null 로 바꾸면 누락이 검증 오류가 아니라 역직렬화 실패가 되어 응답 계약이 바뀐다.
- 컨트롤러 파라미터의 null 가능 여부 — Spring 이 required 판정에 쓴다.
- `data class` 의 `ByteArray` — `equals` 는 참조 비교.
- `companion object` + `@JvmStatic`/`@JvmField` — 프레임워크(JUnit, Testcontainers, 리플렉션)가 요구하는 경우.
- `internal` 금지 멤버 — 템플릿·리플렉션이 이름으로 찾는 멤버.
- `serialVersionUID` 고정, top-level `main` 과 `setMainApplicationClass`, `open` 없이 프록시가 되는 이유(kotlin-spring).
- 파일 최상위 `private val log`·top-level 함수 — 처음 등장하는 대표 파일에서만.
- Java 와 결과가 다른 표준 함수(`trim`, `split`, `JsonNode.map` 등).

같은 설명을 같은 파일 안에서 반복하지 않는다. 여러 파일에 같은 패턴이 있으면 각 파일에서 한 줄로 이유만 적고,
일반론은 쓰지 않는다. `docs/superpowers/notes/kotlin-conversion-patterns.md` 의 함정 표가 무엇이 실제 함정이었는지의 근거다.

### 3.4 문체 — 사람이 쓴 것처럼

- **그 파일의 기존 주석과 같은 말투·형식을 따른다.** 한국어 주석은 이 저장소의 관례대로 짧은 평서("~한다", "~용.", 명사형 종결).
  새 주석은 한국어. 영어 주석만 있는 파일에 한 줄 덧붙이는 경우에도 한국어로 쓴다(저장소가 이미 섞여 있다).
- 금지:
  - "이 클래스는 ~를 담당합니다", "~하는 역할을 합니다" 같은 합니다체 소개문.
  - 구분선(`// =====`, `// -----`), 섹션 배너, 이모지, 굵게 표시.
  - `NOTE:`, `IMPORTANT:`, `주의:` 머리말의 남발. (기존에 쓰던 파일에서 같은 용도로 한 번 쓰는 것은 된다.)
  - 모든 메서드에 같은 틀의 KDoc 을 붙이는 것, 항목 수를 맞춘 불릿 목록.
  - "~를 보장합니다", "~를 위해 설계되었습니다", "견고한", "효율적으로" 같은 수식.
  - 코드에 없는 미래 계획·권고("추후 ~하는 것이 좋다").
- 길이는 내용이 정한다. 한 줄이면 한 줄, 어려운 곳은 여러 줄. 길이가 고르면 안 된다.
- 한 주석에 근거 하나. 왜 그런지 모르면 쓰지 않는다.

## 4. 범위

본 코드만: `core`(Java 111), `webauthn`(Java 60), `passkey-app`(Kotlin 38), `admin-app`(Kotlin 162), `sdk-java`(Java 25), `rp-app`(Java 35).

- `rp-app` 은 2026-06-30 에 고객사 관점으로 주석을 전면 재작성했고 흔적 표기가 0건이다. 검토만 하고 사실상 변경 없음을 예상한다.
  고객사 샘플이므로 "프로젝트 내부자용" 설명을 넣지 않는다.
- `sdk-java` 는 외부에 나가는 jar 다. 공개 API 의 Javadoc 은 SDK 사용자가 읽는다 — 내부 사정(모노레포, 서버 구현)을 쓰지 않는다.
- `sdk-java` 주석 변경으로 **재배포하지 않는다.** 버전(1.1.0)·CHANGELOG·QA 번들·외부 `passkey_rp` 의 로컬 jar 는 그대로 두고,
  다음 릴리스에 함께 나간다. 앱 이미지도 이 작업 때문에 다시 빌드하지 않는다.
- `core`·`webauthn`(Java) 은 독자가 Java 에 능숙하므로 가볍게 간다: 흔적 표기 정리, 진입점, 그리고 도메인이 어려운데 설명이 없는 곳
  (WebAuthn 검증 단계, 테넌트 격리 필터, 감사 체인, 키 봉인)만. 이미 설명이 있는 곳에 덧붙이지 않는다.
  Task 규모 기준으로 core 2~3개, webauthn 1~2개 정도를 예상한다.
- `.claude/worktrees/` 아래 사본은 대상이 아니다.

## 5. 접근 방식

검토한 세 가지:

1. **추가만** — 빈 곳과 Kotlin 함정에만 새 주석. diff 가 작지만 흔적 표기가 남아 가독성 문제의 큰 부분이 그대로다.
2. **추가 + 작업 흔적 정리** — 채택. 기존의 정확한 설명과 보안 근거를 보존하면서 잡음을 걷어낸다.
3. **전면 재작성(한국어 통일)** — 일관성은 가장 좋지만 diff 가 매우 크고, 정확한 기존 설명을 옮기다 틀릴 위험이 크다.

사용자가 2 를 골랐다.

## 6. 검증

주석만 바뀌었다는 것을 **기계적으로 증명**한다.

1. **주석 제거 후 동일성** — Java/Kotlin 소스에서 주석을 걷어내고 공백을 정규화한 결과를 작업 전(base)과 작업 후(head)로
   파일마다 비교한다. 차이 0 이어야 한다. 도구는 문자열 리터럴(Kotlin raw string `"""`, 문자열 템플릿, char 리터럴)과
   Kotlin 의 중첩 블록 주석을 구분해야 하며, **쓰기 전에 자체 테스트**로 그 경우들을 확인한다
   (문자열 안의 `//`·`/*` 를 주석으로 오인하지 않는지, 주석이 아닌 줄 변경을 실제로 잡아내는지).
   파일 추가·삭제·이름 변경도 0 이어야 한다.
2. **컴파일** — 전 모듈 `compileJava`/`compileKotlin`/`compileTestJava`/`compileTestKotlin`.
   Javadoc 을 빌드하는 태스크가 있으면(sdk-java) 그것도 통과.
3. **소스·리소스 텍스트를 읽는 테스트** — 그런 테스트가 본 코드 소스 파일을 읽는지 확인하고, 읽는다면 실행한다.
4. **사실성 검토** — 추가·수정한 주석 문장을 코드와 하나씩 대조한다. 구현자와 다른 눈으로 본다.
   과거 문서 작업에서 구현자가 재확인을 생략해 틀린 문장이 들어간 전례가 있다.
5. **보존 검토** — 삭제된 주석 줄을 전수로 보고, 보안·동시성·계약 근거가 빠지지 않았는지 확인한다.
6. **문체 검토** — 3.4 금지 목록을 grep 과 눈으로 확인한다.

전체 `./gradlew build` 는 이 저장소에서 원래 빨갛다(슬라이스 설정 충돌, Oracle 컨테이너 경합). 머지 판정에 쓰지 않는다.
1번이 통과하면 런타임 동작은 같으므로 전체 테스트 실행은 요구하지 않는다.
