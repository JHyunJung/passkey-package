# 감사 Top 10 개선 — 설계

- 근거: `docs/superpowers/audit/2026-10-13-audit-report.md` (2026-10-13 전체 저장소 감사, 항목마다 검증 에이전트 3개 중 2개 이상이 실제 문제로 인정)
- 범위: 보고서의 "기능 변경 없이 바로 적용 가능한 개선 Top 10"만 다룬다. 보고서의 다른 항목은 하지 않는다.

## 1. 절대 제약

**기존 기능 동작은 바뀌면 안 된다.** 정상 사용자가 관찰할 수 있는 결과(HTTP 상태·본문·헤더 의미, 화면 표시, 저장 데이터, 감사 로그 내용, 오류 코드, 수락·거부 판정)는 전후로 같아야 한다. 허용되는 차이는 다음뿐이다.
- 지연·처리량·메모리·DB 부하
- 로그 문자열
- 비밀값이 저장되는 위치가 줄어드는 것(S16)
- 메일 발송 시점이 응답 이후로 밀리는 것(S9). 메일 내용과 수신자는 같아야 한다.
- 숨겨진 브라우저 탭에서 폴링을 멈추는 것(P3). 탭이 다시 보이면 즉시 한 번 새로 고쳐, 보이는 동안의 표시가 이전과 같아야 한다.

각 작업은 **현재 동작을 먼저 고정하는 특성화 테스트**를 추가한 뒤 변경한다. 그 테스트가 변경 전후 모두 통과해야 한다.

## 2. 항목

| ID | 모듈 | 문제 | 개선 방향 |
|---|---|---|---|
| P1 | passkey-app, core | RP 요청마다 BCrypt-12 검증을 하는데, 주석에 적힌 `ApiKeyCache`는 존재하지 않는다 | 성공한 검증만 캐시한다. 키는 apiKeyId, 캐시 항목은 (keyHash, SHA-256(secret))에 묶고 TTL은 짧게 한다. DB 조회와 active·만료 검사는 매번 한다. 캐시가 맞지 않으면 BCrypt로 돌아간다. 주석을 사실대로 고친다. |
| P3 | admin-app, admin-ui | 감사 체인 overview가 audit_log 전체를 두 번 읽고, Sidebar가 숨은 탭에서도 30초마다 호출한다 | 테넌트당 한 번만 읽고 재사용한다. 버킷 경계와 break 이후 집계 결과는 그대로 둔다. 숨은 탭이면 폴링을 멈추고 보이면 즉시 갱신한다. |
| P5 | core (Flyway) | `audit_log (created_at, id)` 정렬에 쓸 인덱스가 없다 | 새 Flyway 마이그레이션으로 인덱스를 추가한다. 스키마 접두사와 권한 관례는 기존 마이그레이션을 따른다. |
| P7 | core | 라이선스 heartbeat RestClient에 타임아웃이 없다 | connect와 read 타임아웃을 넉넉하게 준다. 타임아웃 예외는 기존 네트워크 오류 경로로 처리한다. |
| P6 | core 설정 | afterCommit에서 REQUIRES_NEW로 커넥션을 하나 더 잡아 풀이 고갈될 수 있다 | 풀 크기와 Tomcat 스레드 수의 관계를 설정으로 조정한다. 코드 흐름은 바꾸지 않는다. |
| S8 | core | LicenseGuardFilter가 원본 URI로 예외 경로를 판정한다 | 정규화된 `servletPath + pathInfo`로 판정하고, 원본에 `..`나 `;`가 있으면 예외로 보지 않는다. 정상 경로의 판정은 그대로다. |
| S23 | admin-ui | API 경로 세그먼트를 인코딩하지 않는다 | 공용 `seg()`가 `encodeURIComponent`를 적용한다. 지금의 정상 ID(UUID, base64url 등)는 결과 문자열이 같아야 한다. |
| S20 | admin-ui | 로그아웃 후에도 테넌트 검색 캐시가 남는다 | 로그아웃할 때 `invalidateTenantCache()`를 호출한다. |
| S16 | admin-app | bcrypt 해시가 Redis 세션에 직렬화된다 | `AdminUserDetails`가 `CredentialsContainer`를 구현하게 하고 serialVersionUID를 고정한다. 인증과 MFA 흐름은 그대로다. |
| S9 | admin-app | 비밀번호 재설정 응답 시간으로 계정 존재 여부가 드러난다 | 메일을 커밋 이후 비동기로 보낸다. 응답 본문, 상태 코드, 토큰 저장, 메일 내용은 같다. |

## 3. 비목표
- 보고서의 "기능 변화가 따르는 항목"(S1–S7, Q1 등)은 모두 범위 밖이다.
- 리팩터링과 이름 변경은 위 항목을 구현하는 데 꼭 필요한 만큼만 한다.

## 4. 검증
- 백엔드: 영향받는 모듈의 `./gradlew :<module>:test`가 통과해야 한다. Oracle 통합 테스트가 있으면 그 관례를 따른다.
- admin-ui: `npx vitest run`, `npx tsc -b`, `npx eslint .`이 변경 전보다 나빠지면 안 된다.
- 각 항목마다 "동작이 같다"는 것을 보여 주는 특성화 테스트 또는 근거를 남긴다.
